# Stage 5 — isolated frontend minification candidate

The build writes a separate .performance-build directory from tracked .com frontend sources only. No runtime sources are overwritten, no database, credentials, account backend, private files, or .ru deployment are included. CSS and JS retain their paths so dynamic loading continues to work. Terser does not compress expressions or rename global/local identifiers; classic scripts retain their individual execution boundaries. CSS uses whitespace minification; only consecutive plain stylesheet tags whose source has no special file-relative URLs/imports and is not referenced by JS are bundled, in the original cascade order, using content-hashed filenames. Existing marker-tagged style links are never grouped. Original styles remain in the built output for compatibility.

CI compares original stage-4 source and its optimized copy on the same runner, with identical synthetic network latency, all startup fixtures, and lazy utility interaction tests in Chromium, Firefox and WebKit. Reports raw and gzip sizes and stylesheet request reduction. Actual numbers are not available until the workflow completes.

Before any production use: test UI and storage behavior, update the reviewed server cache allowlist for generated bundle files, arrange version-aware atomic deployment and rollback. The existing VPS update process copies source; it has not been modified to deploy the build. The .com main branch is intentionally unchanged. The earlier stage-4 checks may still be running; a stage-5 candidate is not approval of stage 4.
